# Модель безпеки

## Межі довіри

- **alerts.in.ua** — HTTPS обовʼязково, BearSSL з trust anchors (4× GTS Root).
  `setInsecure()` заборонено (SPEC 85). Зміна CA у alerts.in.ua = оновлення
  прошивки (задокументований компроміс).
- **Web UI** — HTTP у довіреному LAN-периметрі (WPA2/WPA3). HTTPS-сервер на
  ESP8266 непрактичний (SPEC 101). НЕ відкривати порт 80 назовні.
- **OTA URL** — HTTPS + обовʼязковий SHA-256 образу; ширший CA-набір
  (DigiCert/USERTrust/ISRG/GTS) активний лише в OTA-режимі.

## Секрети

- `/secrets.json` на LittleFS: Wi-Fi, API-токен, випадковий ключ provisioning,
  хеш пароля (SHA-256 + випадкова сіль).
- Токен write-only: жоден ендпоінт не повертає його; UI показує тільки
  «налаштовано». В логи не потрапляє.
- **Фізичний доступ до плати = доступ до флешу.** ESP8266 не має secure
  element; шифрування флешу немає. Це задокументоване обмеження (SPEC 92).

## Сесії

- Токен сесії тільки в заголовку X-Auth (не cookie) → CSRF-поверхні немає.
- 4 слоти сесій, TTL 24 год, найстаріша витісняється.
- Login: 5 невдач → блокування 60 с.

## Provisioning

- AP з криптографічно випадковим per-device паролем (виводиться в серіал),
  не універсальним і не похідним від chip ID.
- `/setup` у provisioning-режимі вимагає цей пароль як `setup_key`; на вже
  налаштованому пристрої також доступна звичайна admin-сесія.
- Конфіг, секрети й runtime-state записуються через перевірений тимчасовий файл
  та атомарну заміну з recovery-копією на випадок перерваного запису.
